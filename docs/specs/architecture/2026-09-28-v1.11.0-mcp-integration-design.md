## 一、 问题背景与目标

### 1.1 现状与痛点
Inkstone 在经历了 V2（干净运行时）、V3（三支柱：语义上下文、多智能体、三端前端）以及 v1.8–v1.10 的视觉与交互重构后，系统核心底座已经极其坚固（全量 1325 项自动化测试 100% 绿灯）。然而，Agent 在工具能力层仍受制于一个关键瓶颈：

- **工具生态完全封闭**：内核层 [`src/tools/registry.js`](../../../src/tools/registry.js) 仅硬编码了 12 个内置静态工具（`read`, `ls`, `grep`, `glob`, `shell`, `test`, `git`, `web_fetch`, `memory`, `task`, `ask_user`, `edit`）。当开发者需要连接企业内部数据库、调用 GitHub/GitLab API、操作浏览器渲染器或对接项目 Issue 系统时，Agent 只能笨拙地尝试在 `shell` 中临时拼装 curl 或脚本，既不安全也极易失败。
- **界面存在占位空态**：GUI 侧边栏虽预留了 [`McpView`](../../../gui/src/components/v4/SecondaryViews.jsx) 入口，但当前代码显式标明为“功能规划中 · 概念预览”，缺乏底层驱动与实际交互。

### 1.2 核心目标
在 `v1.11.0` 中完整落地行业标准的 **MCP (Model Context Protocol)** 协议，使 Inkstone 具备动态扩展外部工具与数据源的能力：
1. **协议层兼容**：严格遵循 MCP 规范，原生实现 JSON-RPC 2.0 消息帧通道，首期支持 **stdio 进程管道**（覆盖主流官方及社区 MCP Server，如 PostgreSQL, SQLite, GitHub, Fetch, Filesystem 等），并为后续 SSE/HTTP 远程服务保留扩展面。
2. **零运行时外部依赖（Zero Runtime Dependencies）**：坚守 Inkstone 核心原则，**不引入**重达数十个依赖的官方 TS SDK，使用 Node.js 20+ 原生标准库（`child_process`, `readline`, `events`）手写轻量、可控、高鲁棒的 MCP 客户端。
3. **内核工具注册表动态化（Dynamic Registry）**：为 `ToolRegistry` 提供装配期扩展点，将 MCP 服务动态探测到的工具集合自动转换为 DeepSeek 模型兼容的标准 Function Calling JSON Schema。
4. **统一安全护栏收敛（Unified Guardrails）**：所有外部 MCP 工具**严禁旁路运行**，必须命名空间隔离并无缝纳入现有的 `PermissionEngine` 与 `ApprovalCache`，危险写操作强制挂起索要人类授权。
5. **三端协同与 GUI 全功能落地**：在 `config.json` 中原生支持与 Claude Desktop / Cursor 完全同构的 `mcpServers` 配置，打通 Electron 全双工 IPC，将 `McpView` 从空态占位升级为支持**服务启停、连通性探测、工具目录浏览与参数自检**的可视化中枢。

## 三、 详细组件与协议规范

### 3.1 协议规范与帧交换（JSON-RPC 2.0 纯 JS 实现）
Inkstone 采用轻量且严格的 JSON-RPC 2.0 规范，通过 `\n` 分隔消息帧（标准的 Stdio Line Protocol）：

1. **握手流程（Initialization）**：
   - Client 发送 `initialize` 请求：
     ```json
     {
       "jsonrpc": "2.0",
       "id": 1,
       "method": "initialize",
       "params": {
         "protocolVersion": "2024-11-05",
         "capabilities": { "tools": {} },
         "clientInfo": { "name": "inkstone", "version": "1.11.0" }
       }
     }
     ```
   - Server 回复其支持的协议版本与服务端信息；
   - Client 发送 `notifications/initialized` 握手完成通知：
     ```json
     {
       "jsonrpc": "2.0",
       "method": "notifications/initialized"
     }
     ```
2. **工具发现（Tools Discovery）**：
   - Client 发送 `tools/list`：
     ```json
     { "jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {} }
     ```
   - Server 回复当前具备的工具描述：
     ```json
     {
       "jsonrpc": "2.0",
       "id": 2,
       "result": {
         "tools": [
           {
             "name": "query_database",
             "description": "Execute a SQL query against PostgreSQL",
             "inputSchema": {
               "type": "object",
               "properties": {
                 "sql": { "type": "string", "description": "The SQL query" }
               },
               "required": ["sql"]
             }
           }
         ]
       }
     }
     ```
3. **工具执行（Tool Invocation）**：
   - Client 发送 `tools/call`：
     ```json
     {
       "jsonrpc": "2.0",
       "id": 3,
       "method": "tools/call",
       "params": { "name": "query_database", "arguments": { "sql": "SELECT 1" } }
     }
     ```
   - Server 返回执行结果，结构映射为 Inkstone 文本内容：
     ```json
     {
       "jsonrpc": "2.0",
       "id": 3,
       "result": {
         "content": [{ "type": "text", "text": "[{\"?column?\": 1}]" }],
         "isError": false
       }
     }
     ```

### 3.2 动态工具装配与命名空间隔离
为了防止外部 MCP 工具与内置工具（例如外部服务也叫 `read` 或 `grep`）发生冲突，或多个 MCP Server 之间工具重名，必须实行**两级命名空间隔离**：
- **系统内部识别标识**：`mcp__<serverId>__<toolName>`（使用双下划线拼接）。
- **函数名规范校验**：DeepSeek/OpenAI 要求函数名符合 `^[a-zA-Z0-9_-]{1,64}$`。对于含有非法字符的服务名或工具名，进行安全归一化编码。
- **注册表扩展接口**（修改 [`src/tools/registry.js`](../../../src/tools/registry.js)）：
  ```javascript
  // 装载指定提供方的外部工具集
  registry.mountExternalTools(serverId, toolDefinitions);
  // 卸载或重启指定提供方的工具集
  registry.unmountExternalTools(serverId);
  // 判定是否为 MCP 工具
  registry.isExternalTool(toolName);
  ```

### 3.3 MCP Schema 到 DeepSeek Tool Schema 的转换
DeepSeek 严格遵循 OpenAI 兼容的 Function Calling 协议：
- 将 MCP Tool 的 `inputSchema` 清理并标准化：去除不支持的元关键字（如 `$schema`, `additionalProperties: false` 若造成校验阻碍则做温和过滤）；
- 构造标准的 DeepSeek 工具规范：
  ```javascript
  {
    type: "function",
    function: {
      name: namespacedName,
      description: `[MCP: ${serverId}] ${tool.description || ""}`.trim(),
      parameters: normalizedInputSchema
    }
  }
  ```

### 3.4 统一权限与安全护栏映射
外部工具不可视作纯安全操作，必须深度绑定 Inkstone 既有的安全架构：
1. **权限分类推导（Category Inference）**：
   - 查询/列出/搜索类操作（工具名包含 `get`, `list`, `search`, `fetch`, `query`, `read` 等）推导为 `ToolCategory.READ`；
   - 修改/创建/执行类操作（包含 `create`, `update`, `delete`, `drop`, `exec`, `mutate`, `write`, `send`）推导为 `ToolCategory.EXECUTE` 或 `ToolCategory.DESTRUCTIVE`。
2. **人工审批拦截（Human-in-the-loop）**：
   - 任何推导为高危/变更类的 MCP 工具调用，在命中 `ask` 策略或默认非受信模式时，自动挂起执行循环（`agent-runtime`），发出 `approval:request` 事件，并在 GUI/TUI 弹出审批卡片，用户同意后方可发向 MCP Server 子进程。
3. **工作区边界与超时控制**：
   - MCP 工具调用超时由 `limits.toolCallTimeoutMs`（默认 60s）严格钳制，超时通过 `AbortController` 撤回请求并向 Agent 注入超时错误，杜绝外部进程死锁。

### 3.5 配置结构设计（完全兼容 Cursor / Claude Desktop）
在项目根目录或全局 `config.json` 中引入 `mcpServers` 顶层配置，零心智负担：
```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "d:/workspace"],
      "env": { "NODE_ENV": "production" },
      "autoApprove": ["read_file", "list_directory"],
      "disabled": false
    },
    "sqlite": {
      "command": "uvx",
      "args": ["mcp-server-sqlite", "--db-path", "test.db"],
      "disabled": true
    }
  }
}
```

### 3.6 GUI 可视化管理与 IPC 契约
升级 [`gui/src/components/v4/SecondaryViews.jsx`](../../../gui/src/components/v4/SecondaryViews.jsx) 中的 `McpView`：
1. **服务卡片状态流转**：
   - `DISCONNECTED`（灰色）：未启用或已停止；
   - `CONNECTING`（黄色微光动效）：正在启动子进程并进行初始化握手；
   - `CONNECTED`（绿色常亮）：握手成功，展示其探测到的工具标签；
   - `ERROR`（红色报警）：进程异常退出或握手失败，提供一键重试与错误堆栈折叠展开。
2. **动态工具抽屉/列表**：
   - 点击服务卡片可展开该服务向 Agent 暴露的所有动态工具及参数说明，支持用户手动针对单工具设置“始终允许”或“每次询问”。
3. **IPC 通道注册（`gui/main.js` & `preload.js`）**：
   - `mcp:list`：获取当前所有 MCP 服务的连接状态及发现的工具；
   - `mcp:restart`：强制重启特定服务并刷新注册表；
   - `mcp:toggle`：启用或禁用特定服务。

## 四、 架构决策与边界取舍

| 决策维度 | 选定方案 | 否决项 | 选定理由 |
|---|---|---|---|
| **SDK 选型** | **纯 JS 原生实现 JSON-RPC** | 引入 `@modelcontextprotocol/sdk` | 官方 SDK 携带巨量嵌套依赖与 TS 编译包，破坏项目核心运行时 0 外部依赖原则。原生实现仅需 200–300 行即可覆盖完整需求。 |
| **传输层优先级** | **首选 stdio 进程管道** | 优先做 WebSockets / 复杂网络网关 | 95% 以上的主流 MCP 实用工具（DB、FS、Git）均以 stdio 运行，本地免开端口、无端口冲突与鉴权漏洞。 |
| **工具命名冲突** | **强制带服务名前缀** | 扁平命名 / 随机覆盖 | 避免外部扩展覆盖核心的系统文件读写工具，保证时序日志与安全审计的可解释性。 |
| **权限默认策略** | **写操作默认拦截审批** | 完全信任外部工具 | 外部工具具有访问宿主外部网络与数据库的不可控副作用，必须遵循防御性设计原则。 |

## 五、 关键约束与安全考量

1. **子进程生命周期严格防孤儿**：在 Windows 平台上，子进程的父子树关联较为脆弱。必须在内核关闭、Electron 退出、或服务重启时，使用递归树形信号或 job-object 清理派生的子进程，严禁遗留驻留后台的 node/python 僵尸进程。
2. **环境变量防泄漏**：父进程中的敏感凭据（如全局 API Key）不得默认注入外部 MCP 进程，仅透传 `mcpServers[id].env` 显式指定的变量与系统基本 PATH。
3. **错误处理隔离**：某个 MCP Server 发生崩溃或返回格式错误的 JSON-RPC 响应，只能导致该服务状态置为 ERROR 并自适应重试，**绝对不可击穿内核进程或让 Agent 崩溃**。
