## 1. 为什么是「定级再议」

README [版本命名规则](../../README.md#版本命名规则) 把「触及核心运行时 / 内核契约的**破坏性**重构」列为大版本、由维护者拍板。#10 的硬约束是**非破坏性**(公开 API `send`/`approve`/`interrupt`、事件发布顺序、错误语义、审批暂停–续跑时序全部不变),所以按 patch 可辩护;但它是 1160 行核心运行时的重构,风险面大。

本片只交付零风险的阶段 1–2(不改实现),把「重构是否值得、按什么级别」的决策建立在**真实数据**上,而不是行数焦虑。

### 3.2 四条审批恢复分支的公共样板(重复点)

「暂停 → 保存 → 清理」样板在四处近似重复,差异只在「中间那次操作」:

```
重建 pending_tool_call / 取 resume 上下文
→ grantApprovalForToolCall(带外授权)
→ publishTurnResumed
→ runAfterClearingConsumedPause(operation)      ← 差异点:operation
→ 若 awaiting_approval:
     savePausedRecord({ replaceApprovalId })     ← 重复样板 ①
     transitionLifecycle → awaiting_approval
     currentTurnId = null; currentAbortController = null
     return { status:"awaiting_approval", ..., setTurnStatus(awaiting_approval) }
→ 若 complete:
     clearConsumedPausedRecord / flushEvents      ← 重复样板 ②
     transitionLifecycle → idle
     currentTurnId = null; currentAbortController = null
     return { status:"complete", ..., setTurnStatus(completed) }
→ 若失败 / repair:runRepairLoop 收口            ← 重复样板 ③
```

具体重复点(带行号,当前 HEAD):
- `approve` 内 `savePausedRecord` + lifecycle 迁移 + `currentTurnId/currentAbortController` 置空的块:约 [:351–364](../../../src/core/runtime/agent-runtime.js#L351-L364)、[:413–431](../../../src/core/runtime/agent-runtime.js#L413-L431)、[:462–475](../../../src/core/runtime/agent-runtime.js#L462-L475)。
- `resumeRuntimeVerifierApproval` 与 `resumeRepairVerifierApproval` 两个分支的暂停/续跑/终态收口结构高度同构([:543](../../../src/core/runtime/agent-runtime.js#L543) 与 [:683](../../../src/core/runtime/agent-runtime.js#L683) 起)。

### 3.3 纯函数 vs 副作用分离(阶段 3 的抽取候选)

**已经是纯函数(可原样抽出、零风险)**:
- `verifierApprovalResumeState`(1057)、`verifierPendingToolCallForResume`(1092)、`verifierParamsFromMode`(1104)、`resolveVerifierTestArgv`(1113)、`mapVerifierToolResult`(1124)—— 输入 resume_state + options,输出新 resume_state / 验证器参数。
- `normalizeApprovalDecision`、`budgetSpentOf`、`readPresent`、`firstDefined`、`sanitizeErrorMessage`(1145–1170)。

**副作用封装(已是单一职责,可不动)**:
- `savePausedRecord` / `clearPausedRecord` / `clearConsumedPausedRecord` / `runAfterClearingConsumedPause` / `throwAfterClearingConsumedPause` / `publishTurnResumed` / `publishTurnPaused` / `deletePausedSidecar`。

**编排(阶段 4 的拆分候选)**:
- `send` / `approve` / 两条 verifier resume 分支。候选拆分:
  - `ResumeStrategies`(spec 原建议落 `src/core/runtime/resume-strategies.js`):把「暂停-保存-清理」样板参数化,四分支各传一个 `operation` + 终态映射,收敛到一个 `resumeWithStrategy(approvalRecord, { execute, onComplete, onRepair })`。
  - 生命周期状态机驱动与阶段执行分离:把 `transitionLifecycle` / `setTurnStatus` / `currentTurnId` 置空这类「迁移」与「具体做某事」解耦。

## 4. 阶段 3–4 候选方案(未开工,仅供定级参考)

1. **抽 `resume-strategies.js`**:把 3.2 的样板收敛成 `resumeApproval(record, operation)` 参数化实现;四条分支只留「operation 本身」与「终态差异」。**风险:** 中 —— 样板已由刻画测试锁住,抽错会立刻变红。
2. **抽纯函数族**:3.3 的纯函数原样迁出,`agent-runtime.js` 只留 import。**风险:** 极低。
3. **生命周期状态机拆分**:生命周期迁移(状态/事件)与阶段执行分离。**风险:** 高,建议在 1、2 之后单独评估。

**硬约束(阶段 3–4 开工时逐条验收)**:公开 API(`send`/`approve`/`interrupt`)、**事件发布顺序**(7 条刻画测试 + 现有集成测试原样全绿)、**错误语义(code/message)**、审批暂停–续跑时序**全部不变**。验收看边界清晰度与测试可独立性,**不看行数下降**。
